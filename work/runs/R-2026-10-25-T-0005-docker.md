# Run: Docker setup — an app image and a compose file with Caddy (HTTPS only), runnable on this machine

> Opened at the start of the session and added to as it goes. Not written at the end.

## What is different now

LinkSink can now run on this computer in Docker, at https://localhost, the way it will run on a server: one command
builds it and starts two containers, the app and Caddy in front of it serving HTTPS only. You sign up, the
confirmation link appears in the app's log (no mail is sent on this machine), you sign in and save links, and
they are still there after the containers are stopped and started again. The same image serves any host name: only
the name in the settings file changes. The steps are in deploy/README.md.

## Deviations from the plan

1. **Stopping while the app is still fetching page details ends with a kill, not a clean exit.** done_when 9 holds
   when the fetch queue is idle (`docker compose stop`: 0.85 s, exit 0). Right after an import, while the queue
   still has links to fetch, node does not exit after SIGTERM and Docker kills it: exit 137, 3 times out of 3. The
   cause is in the app (the fetch queue keeps node's event loop alive and nothing stops it on shutdown), and the
   brief keeps the app's code as it is, so it is not fixed here: proposed task 1 below. No data is at risk (SQLite
   WAL keeps every committed write; waiting links are fetched again at start).
2. **The plain-http check ran on port 8080, not 80.** Port 80 on this machine belongs to Apache running in WSL
   (wslrelay.exe forwards it to Windows' 127.0.0.1:80), so the stack cannot publish 80 here while Apache runs. For
   my runs a scratch override published http on 127.0.0.1:8080; https stayed on the real 443. The literal
   `curl -I http://localhost/login` will reach Apache until the person stops it; deploy/README.md tells them to.
3. **Two adapter-node settings the task's Context did not name:** `ADDRESS_HEADER=X-Forwarded-For` and
   `XFF_DEPTH=1` on the app (compose.yaml). Without them the /login and /signup forms pass Caddy's address to
   Better Auth, and every browser shares one rate-limit bucket (shown below). Settings only, no app code; the
   Context's conclusion (no app change) stands.
4. **Settings carry a `LINKSINK_` prefix** and the example is `deploy/env.example`: compose reads the same top-level
   `.env` as `npm run dev`, so the prefix keeps the two apart; the app gets its own names through compose. One
   setting beyond the task's list, `LINKSINK_LISTEN` (127.0.0.1 here, empty on a server), keeps ports 80 and 443
   on this computer's loopback while testing.
5. **The deps stage removes what the lockfile marks `devOptional`** after `npm ci --omit=dev`: without it drizzle-kit,
   vite, svelte, @sveltejs/kit, vitest and typescript stay in the image (optional peers of better-auth).
